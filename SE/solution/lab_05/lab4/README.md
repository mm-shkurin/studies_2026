## Соответствие кинотеатр → аэропорт

| Образец (кинотеатр) | Вариант 5 (аэропорт) |
|---|---|
| Зритель / кассир | Пассажир / киоск или веб-клиент |
| Сеанс (`session`) | Рейс (`Flight`) |
| Место в зале | Место в самолёте (`Seat`) |
| `Ticket` | `BoardingPass` (или `Ticket` — выбрать одно имя и держать во всех 6 моделях) |
| Каталог фильмов | Каталог рейсов (`IFlightCatalog`) |
| Booking / SeatHold | Booking / удержание места на рейсе |
| Redis TTL удержания | TTL брони до оплаты |
| RabbitMQ → уведомление | Очередь → посадочный талон / письмо |

Статусы (ориентир, согласовать с контрактом и автоматом):
`RESERVED_LOCK` → `PAID_CONFIRMED` → `CHECKED_IN`; альтернативы: `CANCELLED_EXPIRED`, `REFUNDED`.

## Пошаговый план

### Шаг 1. Соглашения
1. Зафиксировать имена сущностей из ЛР 2–3 (`Flight`, `Seat`, `Booking`, `BoardingPass`, `Passenger`).
2. Заполнить таблицу каналов (как табл. 2 в образце): Web→API, API→PostgreSQL, API→Redis, API/worker→брокер, внешние платёж и уведомления.
3. Для каждого канала указать: прикладной протокол, TLS, TCP-порт, IPv4, канальный стандарт.

### Шаг 2. Диаграмма 1 — физическая топология
1. Узлы: устройство пассажира, (опционально) стойка/киоск, сервер приложений, PostgreSQL, Redis, брокер, платёжный провайдер, провайдер уведомлений.
2. На рёбрах — полный стек (не только «HTTP»).
3. В заметках: оплаченный билет живёт в БД; TTL Redis не удаляет оплаченную продажу.

### Шаг 3. Диаграмма 2 — процессы и артефакты
1. Внутри устройств — `executionEnvironment` / артефакты: API, payment boundary, worker уведомлений.
2. API и платёжная граница в одном процессе допустимы; worker — отдельно, событие через брокер.
3. Указать outbox / идемпотентность consumer (как в обосновании образца).

### Шаг 4. Диаграмма 3 — контракт
1. Класс `BoardingPass` (или `Ticket`) с закрытыми атрибутами: id, flightId, seatId, цена в копейках, status, paymentTransactionId.
2. Публичные операции: reserve, markPaid, checkIn, cancel, refund; защищённая `canRefund`.
3. Enum статусов; заметка про одну активную продажу на пару рейс/место.

### Шаг 5. Диаграмма 4 — автомат состояний
1. Переходы в форме `событие [условие] / действие`.
2. Из удержания: оплата, отмена, истечение TTL.
3. После `CHECKED_IN` возврата нет; повторная доставка того же payment id — идемпотентна.

### Шаг 6. Диаграмма 5 — компоненты
1. UI (Web/киоск), Booking Service, Flight/Schedule Service, SeatHold, PaymentGatewayBoundary, Notification Worker, Persistence, FlightCatalogBoundary.
2. Интерфейсы: `IBooking`, `IFlightCatalog`, `ISeatHold`, `IPayment`, `INotificationQueue`, `IPersistence`.
3. Сплошная линия к интерфейсу — предоставление; пунктир — использование.

### Шаг 7. Диаграмма 6 — ERD
1. Сущности: Flight, Seat, Booking/BoardingPass, Payment (по необходимости).
2. Составные FK / уникальность места в рейсе; частичный уникальный индекс на активные статусы (исключить двойную продажу).
3. Цена ≥ 0 в копейках; история оплат не удаляется каскадом без причины.

### Шаг 8. Согласование и отчёт
1. Одинаковые имена статусов в контракте, автомате и ERD.
2. Имена компонентов и протоколы совпадают с deployment.
3. Собрать `report.md` по образцу → конвертировать в `report.docx`.
